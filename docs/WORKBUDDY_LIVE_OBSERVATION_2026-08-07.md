# WorkBuddy 现场陪跑与太极观察窗对照

> 日期：2026-08-07 20:18-20:36（Asia/Shanghai）  
> 任务：制作一个抖音摄影师工作台 HTML Demo，包含每日脚本、完成/未完成状态、拍摄内容和波普漫画风界面。  
> 目的：观察 WorkBuddy 的真实运行链路与信息流展示，提取可用于太极的设计原则，而不是照抄外观。

## 一、实际运行链路

1. 主代理先建立 3 个结构化任务：
   - 产出拍摄脚本与任务的仿真数据。
   - 设计波普漫画风视觉系统。
   - 搭建工作台页面与交互。
2. 前两项互不依赖，主代理并行派给内容策划和美术指导两个子代理。
3. 内容代理生成 `scripts/data.js`，交付 5 天、17 个任务、72 个分镜及完整状态分布。
4. 美术代理生成 `styles/popart.css`，经历多轮“编辑 -> 命令检查 -> 再编辑”，最终交付 709 行设计系统。
5. 主代理等待两个前置产物返回，然后依次生成 `index.html`、`styles/app.css` 和 `scripts/app.js`。
6. 主代理执行 JS 语法、数据字段、任务数量、分镜数量、日期、灵感和设备清单检查，并检查关键 CSS 交互规则。
7. 主代理修正整合问题，将 3 个任务统一更新为 `completed`，写出最终说明并调用产物展示入口。

这不是所有成员同时开工，而是“可独立工作有限并行，整合步骤等待前置结果”的依赖式协作。该原则符合太极的自主智能体团队目标。

## 二、WorkBuddy 的工作方法

这次最值得学习的不是它用了哪些控件，而是主代理如何把一个自然语言需求变成可交付项目。整个过程没有要求用户逐步教它，也没有把项目降级成预设工作流。

### 1. 先理解交付物，再决定是否组队

用户只给出了产品目标、核心内容、风格和交付形式。WorkBuddy 没有先从固定员工目录里机械匹配人名，而是先判断最终需要五类产物：业务数据、视觉系统、页面结构、交互逻辑和验证证据。

然后它只把真正可独立完成的两部分交给专业子代理：

- 内容策划负责业务数据。
- 美术指导负责视觉系统。

页面整合和最终交付由主代理自己承担。它没有为了看起来像团队而拉满角色，也没有把每一个微步骤都变成独立员工。

太极要学习的是“按产物能力边界组队”，不是“按关键词从员工池凑人数”。成员选择的输入必须是完整项目目标、交付物列表、当前缺口和依赖关系。

### 2. 计划是动态任务图，不是固定流水线

主代理创建了 3 个任务，但只并行执行其中两个。第三个整合任务天然依赖前两个产物，因此留在主代理手中等待。

实际依赖关系是：

`内容数据 ─┐`

`视觉系统 ─┴─> 页面整合 -> 自动检查 -> 修正 -> 最终交付`

这说明任务列表只是协调账本，真正的执行顺序由依赖和当前证据决定。WorkBuddy 没有为了遵守任务编号而串行等待，也没有让 QA、前端和策划同时对着空输入工作。

太极需要的是可修改 DAG：主代理可随结果质量增加、取消、替换或重排任务；只有互不依赖的工作有限并行。用户插话时更新目标和任务图，而不是继续执行旧队列。

### 3. 子代理收到的是“产出合同”，不是一句口头通知

每个子代理的任务包含：

- 专业身份和使用场景。
- 唯一输出文件路径。
- 必须遵守的数据结构或视觉规范。
- 数量、字段、兼容性和质量要求。
- 完成后的简短回报格式。

例如内容策划不仅被要求“写点拍摄数据”，还拿到了日期范围、任务数量、状态分布、字段结构、专业细节和禁止项；美术指导拿到了颜色、边框、网点、组件、动效、无障碍和离线字体约束。

因此员工不需要重新猜主代理的意图，主代理也能按合同验证结果。太极的团队调度不能只发送原始用户消息，必须由主代理生成结构化任务合同。

### 4. 子代理拥有局部自主权

美术指导并不是写一次 CSS 就结束。它自行执行了多轮：

`实现 -> 命令检查 -> 发现问题 -> 编辑修复 -> 再检查`

整个过程中没有向用户询问“下一步怎么做”，也没有把每次工具调用升级成审批。只有结果满足自身完成条件后才交回主代理。

太极员工需要在责任边界、预算和安全策略内拥有局部闭环能力。局部失败首先由责任员工修复；连续失败或发现目标冲突时，才交给主代理重新规划；涉及外部发送、付费、删除或敏感授权时，才请求用户决定。

### 5. 主代理保留项目所有权

主代理没有把两个子代理的文件直接当成最终产品。它等待结果返回后执行了以下动作：

- 回读子代理产物。
- 检查关键 CSS 结构和点击穿透规则。
- 检查 JS 语法。
- 加载数据并统计日期、任务、分镜、状态、灵感和设备数量。
- 自己编写整合页面和交互逻辑。
- 根据检查结果继续修改 HTML 与 CSS。
- 最后统一更新任务状态并组织交付说明。

这与太极当前“分派后等待员工各自回复”的模式不同。自主团队必须有一个持续持有原始目标、验收标准和整合责任的主代理。员工交付只是输入，不是项目完成。

### 6. 安全本地操作默认自主完成

本次写文件、读取文件、运行 Node 语法检查和统计数据都没有打断用户请求确认。任务从 20:18 持续运行到 20:34，中间不需要用户逐步放行。

这不是取消安全边界，而是把动作分层：

- 项目工作区内的安全读写、构建和验证可自主执行。
- 外部发布、发送、账号授权、付费、删除和敏感路径操作才进入人工确认。

太极若对所有动作都审批，会退化为需要用户推动的工作流；若全部放开，又会失去安全边界。正确做法是能力、路径、风险和目标四维授权。

### 7. 先产出可见候选，再继续验证

主代理在整合过程中就打开右侧预览，让用户知道项目确实在形成；后续 CSS 和 JS 写入后，预览自动刷新。最终交付时再把文件列表、预览、全部产物和全部变更放在一起。

这个过程让产物成为项目状态的一部分，而不是最后一句“已经完成”。太极也应持续登记产物版本，但必须标明“生成中、待验证、可验收”，避免把半成品误当成最终结果。

### 8. 项目上下文有物理边界

WorkBuddy 为本次任务创建了新的时间戳工作空间，并在完成后写入项目内记忆文档。代码、数据、任务记录、子代理记录和项目记忆都能按本次会话追溯。

这与把所有产物堆在仓库根目录不同。太极每个新项目必须建立独立 `projectId`、工作空间、任务账本、产物索引、回放和项目记忆；只有用户明确继承旧项目时才挂接旧上下文。

### 9. 它表现自然的原因

WorkBuddy 看起来比刚性工作流自然，主要不是因为文案更像人，而是因为：

- 模型先做语义判断，调度器服务模型决策，而不是调度器替模型决定。
- 任务粒度围绕真实产物，不围绕工具次数。
- 主代理能根据中间结果继续行动，不需要预先写死全部步骤。
- 子代理有局部自主纠错空间。
- 主代理始终持有项目目标并负责整合。
- 安全本地动作不会反复等待人工放行。
- 完成由产物和验证证据定义，不由“模型回复了一段话”定义。

这正是太极从“智能体驱动的工作流”升级到“自主智能体团队”的核心差距。

## 三、太极内核需要吸收的能力

### 1. 交付物规划器

模型先产出：项目目标、交付物、验收标准、依赖和能力缺口。团队匹配器只能根据这份结构化计划选人，不能直接从最后一条聊天文本猜员工。

### 2. 动态团队与任务合同

主代理按需要创建最小团队。每个成员任务必须包含输入、输出、边界、验证方式、预算和升级条件。换人、加人和删除成员直接修改当前团队版本，并让旧提案失效。

### 3. 有限并行的自适应任务图

无依赖任务可并行；整合、审核和发布必须等待前置证据。主代理可以根据失败重新规划，而不是把最初队列执行到底。

### 4. 员工局部闭环

责任员工在最大尝试次数内自行实现、验证和修复。失败证据要回到同一责任员工；跨模块问题由主代理拆解后重新分派；不能每次失败都要求用户教下一步。

### 5. 主代理整合与完成门

主代理对最终产品负责。所有子产物必须经过回读、集成和证据检查。只有交付物、运行结果、核心操作和必要人工确认全部满足时，项目才能进入 `completed`。

### 6. 项目级上下文与记忆

新对话默认产生新的 `conversationId` 和项目草案；新项目拥有独立工作空间、团队版本、任务图、产物索引、审批、回放和记忆。长期用户记忆可以跨项目读取，但项目任务和审批不能自动继承。

### 7. 风险分级授权

允许安全的本地实现和验证自主运行；外部发送、授权、付费、删除、密码和敏感数据操作必须停下来确认。审批必须绑定当前 `projectId`、`proposalId` 和版本号。

### 8. 可观察但不暴露私有思维链

用户应看到目标理解、公开执行摘要、责任人、当前动作、依赖、返工原因、产物和验证证据。模型私有思维链不作为产品功能；需要的是可核验的决策摘要和行动证据。

## 四、观察窗值得吸收的部分

### 1. 主信息流很克制

默认只显示：

- 用户原始需求。
- 一句主代理意图，例如“我来搭个小团队干这个活”。
- 可折叠任务列表。
- 一行动态状态，例如“正在写入文件”“正在编辑文件”“等待模型响应”。

工具命令、心跳、租约和内部技术事件不占据主聊天区。技术细节应进入折叠区或诊断视图。

### 2. 动态状态稳定且不抢视线

状态被压缩在任务卡下方的一行，不改变整体布局，也不制造持续滚动。它比太极当前高频全量事件流更适合长任务。

太极可吸收状态类型，但不应只用模糊文案。建议固定展示：

`负责人 · 当前动作 · 当前对象 · 已持续时间`

例如：`美术指导 · 验证样式 · popart.css · 1分42秒`。

### 3. 产物随任务常驻预览

生成 `index.html` 后，WorkBuddy 自动在同一窗口右侧打开预览。后续文件补齐时，预览自动刷新为完整页面。最终消息下方还显示独立产物卡：

- 文件名和大小。
- 打开文件或预览入口。
- 查看全部产物。
- 查看全部变更。

太极产物中心应吸收这一模式：观察窗显示产物摘要，点击后在当前项目上下文打开预览、文件或所在目录。

### 4. 专业角色拿到明确产出合同

子代理不是收到一句模糊的“帮忙做设计”，而是获得文件路径、数据结构、字段约束、设计规范、完成条件和返回格式。主代理负责整合，不把各成员输出直接拼成最终产品。

太极的任务对象需要固定包含：负责人、输入、输出路径、完成条件、验证命令、依赖和最大返工次数。

### 5. 自主纠错发生在成员内部

CSS 子代理连续执行多次编辑和命令验证，直到行数、括号和关键组件约束通过才返回。用户不需要逐步教它修复。

太极应允许责任员工在预算内自行形成“实现 -> 验证 -> 修复”小闭环，只有连续失败、风险操作或需求冲突才升级给主代理或用户。

### 6. 交付说明可扫描

最终答复按角色产物、界面结构、关键交互和运行方式组织，并明确离线可用、数据持久化和重置能力。项目标题也根据任务语义生成，而不是复用最后一句聊天文本。

## 五、WorkBuddy 自身暴露的问题

### 1. 可见任务状态更新滞后

两个子代理已经返回结果时，任务列表仍显示空心未完成；底层实际存在的第三个整合任务没有在界面中展示。直到接近最终交付，3 项状态才一起更新为 `completed`。

太极必须区分：

- `queued`：等待前置条件。
- `running`：真实执行中。
- `submitted`：员工已提交，等待主代理整合或审核。
- `reworking`：验证失败后返工。
- `completed`：证据通过。

任何成员结果返回后应立即增量更新，不能等最后统一刷新。

### 2. 状态文案准确度不足

“正在写入文件”“等待模型响应”简洁，但没有负责人、文件、验证目标或阻塞原因。用户仍无法判断当前是正常等待、模型卡住还是执行器失联。

### 3. 中间预览会出现明显半成品

`index.html` 首次打开时，CSS 和 JS 尚未写完，页面显示大块空白和未渲染内容。实时预览有价值，但必须标注“生成中，尚未验证”，不能让用户误认为这是候选交付物。

### 4. 验证以静态检查为主

现场确认执行了 JS 语法和数据完整性检查，也尝试寻找浏览器截图工具；没有看到完整的交互自动化、响应式截图或点击路径验证。最终页面从画面上已正确渲染，但关键交互仍主要依赖实现说明。

太极的完成证据至少应包括：

- 语法/构建结果。
- 页面可打开且非空。
- 核心操作路径通过。
- 产物路径和修改时间。
- 必要时的桌面/窄屏截图。

### 5. 最终答复混入无关记忆采集

完成项目后，WorkBuddy 追加询问用户称呼、城市和工作方向。该内容与本次交付无关，削弱了完成消息的确定性。

太极的项目完成消息只包含完成证据、产物入口、验证结果、已知限制和下一步。长期记忆采集必须独立展示，且不阻塞交付。

## 六、太极观察窗建议结构

### 默认层（持续可见）

1. 项目状态：阶段、进度、运行时长、真实执行人数。
2. 当前工作：负责人、动作、对象、耗时。
3. 最近有效进展：只显示产出、验证、返工、阻塞和人工决定。
4. 阶段小结：完成了什么、证据是什么、还差什么、下一步是什么。
5. 产物入口：预览、打开文件、打开目录、复制路径。
6. 聊天输入：始终保留在主信息流底部，明确发送到当前项目的主代理；用户插话立即进入当前项目上下文并触发重新评估，不能排在旧任务队尾。

### 展开层

1. 团队成员状态与依赖关系。
2. 任务 DAG 和等待原因。
3. 工具调用摘要与命令结果。
4. 心跳、租约、检查点和原始日志。

### 状态呈现原则

- 主聊天最多保留 4 行动态过程，超出折叠，不推动历史消息持续滚动。
- 右侧观察栏展示完整业务时间线，但心跳和工具碎片默认折叠。
- 只把真实 `running` 员工显示为工作中。
- `pending` 必须写明等待谁或等待什么。
- `awaiting_user` 必须有绑定当前提案版本的可操作确认卡。
- 暂停和停止必须显示主任务、子任务与执行进程的实际确认结果。

## 七、重构验收标准

1. 用户能在 5 秒内看出谁在做什么、为何等待、下一步是什么。
2. 观察窗高频运行 30 分钟时，聊天滚动和输入仍保持流畅。
3. 子任务完成后 300ms 内增量显示为“已提交”或“已验证”。
4. 产物创建后可在项目内直接预览，并可打开本地文件和所在目录。
5. 中间预览明确标记未验证状态；只有证据通过的版本可标为“可验收”。
6. 暂停或停止后，所有子任务、租约、心跳和外部进程均不再推进。
7. 完成消息不混入新项目、旧审批或无关记忆采集。
8. 用户插话后 300ms 内显示已接收状态，旧计划停止继续扩展；主代理随后明确给出继续、修改、暂停或重新分派的结果。
