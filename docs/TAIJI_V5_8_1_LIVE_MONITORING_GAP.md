# 太极 v5.8.1 真实陪跑与运行监控缺口

## 样本

- 对话：`章北海助理-对话-2026-08-07.md`
- 陪跑导出：`taiji-autonomy-evaluation-1786094157189.json`
- 陪跑区间：2026-08-07 17:04:28 至 17:15:55，共 686245 毫秒
- 真实任务：`task-1786093847515-a2ae2d38`
- 项目：`conversation-project-conversation-assistant-1786093548902-e68cy`

## 已确认事实

1. 原始需求是制作“每日拍摄脚本工作台”Demo，并由助理选择合适成员设计风格和 GUI。前三次助理均口头表示要开始，但没有创建可执行任务。
2. 用户追问“重新想想该拉什么人、目标是什么”后，系统才创建任务，却把这句纠正误判为独立新任务：`turnRelation=new_task`、`correction=false`，任务合同的目标也被改成了这句追问。
3. 任务决策模型当时不可用，运行时采用确定性回退；生成的团队策略为 `requiresTeam=false`，只指定 `assistant`，因此没有按原始目标组建专业团队。
4. 当前助理执行工具集中没有组建团队、创建提案或调度员工工具。模型随后两次使用 `search_tools` 搜索团队调度能力，均返回未找到。
5. 任务实际上写出了 `每日拍摄脚本工作台.html` 和 `拍摄脚本工作台-团队方案与目标.md`，项目事件账本也登记了三个产物事件；但最终聊天只显示“还没有完成”，没有向用户展示已经产生的文件和下一步缺口。
6. 执行中发生 13 次工具尝试、15 次模型调用，并多次完整读取约 32 KB 的 HTML。一次 `read_file` 参数类型错误、一次网页产物验收契约错误、两次团队工具检索失败。最终因约 480000 Token 的预算停止并保存检查点。
7. 同期渲染器日志反复报告旧记忆层容量超限 `2611/2600`，随后又出现团队状态保存 `QuotaExceededError`。这些异常既没有进入本次任务诊断，也没有进入陪跑导出。
8. 本轮陪跑只产生 4 条记忆检索观察，覆盖率为 `1/24`；任务完成率、误执行率、恢复率、工具调用和驻留指标的分母均为 0。原因是当前陪跑只读取终态任务、记忆检索和 Skill 灰度记录，而本任务最终是 `paused/checkpointed`。
9. `operationDiagnostics` 已存在，但本次助理工具预检失败、语义误判、预算停止和渲染器存储异常均没有形成同一任务下的诊断记录。当前数据源是存在的，但关联和覆盖范围不完整。

## 根因分类

- 任务语义：纠正被识别为新任务，原始目标没有成为活动任务目标。
- 能力暴露：助理运行时看不到团队提案与成员调度能力。
- 执行效率：大文件被重复完整回读，缺少按证据需要读取和重复动作抑制。
- 完成判断：真实产物已登记，但终态总结没有按“已完成 / 未验证 / 待继续”拆分。
- 观测体系：陪跑只做场景结果抽样，不能还原模型、工具、调度、资源和界面错误的完整链路。
- 持久化健康：旧记忆层和团队状态的浏览器存储已接近或超过容量上限。

## 监控台结论

应新增“运行监控台”，但它不能成为新的平行事实源。应先统一事件信封和关联 ID，再把现有任务账本、项目事件、操作诊断、模型调用、工具调用、窗口错误、持久化错误和资源指标投影到监控台。自治陪跑继续负责长期评分，监控台负责实时事实与故障定位；陪跑评分应改为消费统一监控事件。

监控事件至少包含：`eventId`、`occurredAt`、`sessionId`、`conversationId`、`projectId`、`taskId`、`stepId`、`attemptId`、`traceId`、`parentSpanId`、`actorId`、`modelId`、`toolCallId`、事件类型、状态、耗时、Token、错误分类、证据 ID 和脱敏后的公开摘要。不得记录模型隐藏推理或密钥。

## 下一阶段为什么先做它

当前项目不是“没有日志”，而是事实分散在聊天记录、任务运行 JSON、项目 `events.jsonl`、操作诊断、Electron 日志、浏览器存储和陪跑导出中。一次真实故障需要人工跨多个文件拼接，普通用户只能描述界面现象，开发者也容易只修看得见的一层。

如果继续先修单个语义误判、单个工具参数或单个界面提示，下一个问题仍然需要重新猜测根因。统一运行轨迹是后续任务语义、团队调度、Token 治理、存储治理、恢复和真实陪跑优化的共同基础。先把事实链打通，之后每次升级才能根据真实证据选择共性短板，而不是根据截图逐个增加通道。

## 下一阶段固定目标

下一阶段定为 `v5.9.0：统一运行轨迹与监控台`。核心不是制作一个日志页面，而是建立唯一的可观测事件协议，并让监控台、导出诊断包和自治陪跑共同消费该协议。

必须完成：

1. 定义统一遥测事件信封、事件类型、关联 ID、脱敏规则、保留期和版本迁移。
2. 接入用户操作、任务语义判断、任务合同、团队提案/成员调度、模型请求、工具调用、Worker 状态、审批、恢复、产物、验收、窗口错误、持久化错误和资源指标。
3. 把现有 `task-runtime`、项目事件和 `operationDiagnostics` 作为事实来源接入，不复制完整大字段，不建立互相冲突的新任务状态。
4. 在“设置 -> 诊断中心”增加运行监控台，默认用普通用户能理解的阶段时间线展示当前任务；原始技术事件按需展开。
5. 导出一个脱敏问题包，至少包含 Markdown 摘要、JSON 事件、聊天记录、附件清单、任务/项目快照、错误分类、版本和必要环境信息。
6. 让真实陪跑从统一事件轨迹计算场景覆盖，暂停、检查点、失败和进行中的任务也必须可观察，不能只等待终态任务。

## 明确非目标

- 不为“拍摄脚本”“拉团队”或本次措辞增加关键词特例。
- 不在监控台记录或展示模型隐藏思维链、`reasoning_content`、密钥或完整凭据。
- 不新增第二套任务状态机、第二份产物账本或第二份团队事实源。
- `v5.9.0` 先解决“事实能完整还原”；自动根因建议和异常规则进入 `v5.9.1`，长期资源治理进入 `v5.9.2`。

## v5.9.0 执行顺序

1. 盘点并映射现有事件源，写出统一事件协议和迁移边界。
2. 建立主进程追加式事件账本、索引和查询/订阅 IPC。
3. 为语义决策、模型、工具、团队、任务、产物、窗口与存储补齐事件适配器。
4. 建立监控台的任务摘要、阶段时间线、告警、Token/耗时和证据视图。
5. 实现脱敏诊断包导出和重启后回放。
6. 用本次真实任务复跑：监控台必须能直接说明原目标、误判点、未组队原因、工具失败、已生成文件、预算停止和界面存储异常。
7. 完成单元、集成、Electron UI、长任务和导出完整性验证，再更新人格、交接、差异矩阵和版本复盘。

## v5.9.0 验收标准

- 用户发送任务后，无论成功、失败、暂停或卡住，监控台都能在 5 秒内显示当前阶段、负责人、已耗时和最后一个真实动作。
- 任意模型请求和工具调用都有开始/结束、耗时、状态、错误分类与关联任务；Token 异常增长可以定位到具体调用和重复内容来源。
- 纠正、插话和恢复必须显示它们修改了哪个目标、任务或计划；不能只看到新的聊天文字。
- 已产生的文件和证据必须出现在任务时间线中；最终未完成时明确区分“已产生、未验证、仍待完成”。
- 一键导出的问题包足以让另一台电脑上的开发者在不访问用户真实数据目录的情况下还原本次故障链路。
- 监控事件不会泄露密钥、隐藏推理或附件正文中的敏感信息；事件账本可轮转、可恢复、可验证。
