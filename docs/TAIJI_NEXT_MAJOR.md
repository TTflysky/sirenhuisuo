# 太极：下一大版本设计蓝图

> 产品名：太极
> 原则：吸收经过验证的理念，转化为太极自己的能力；不复制外部产品的品牌、界面或实现。

## 1. 产品定位

太极是面向个人与小团队的桌面多智能体办公平台。它把员工、团队、工具、技能、知识库和真实交付物放在同一套可观察、可纠错、可验收的工作流里。

用户只需要描述目标。太极负责判断前提、选择路径、调用合适的员工或工具、验证真实结果；只有确实需要账号、授权、验证码、文件或业务决定时，才用通俗语言请用户参与。

## 2. 不变的产品原则

1. **自己的产品**：不接入或安装 Hermes Agent，不复制其名称、UI 或工作流；只参考公开文档中的工程思想。
2. **真实优先**：工具成功不等于目标完成。每个任务必须有可观察的结果、验收条件和交付记录。
3. **自主但有边界**：先自行排查、纠错和换路线；出现外部阻塞时及时停止重复尝试并清楚交接。
4. **人能看懂**：默认展示结论、进度和下一步；原始命令、参数、日志放在可逐项展开的执行记录中。
5. **状态统一**：助手、员工私聊、团队任务、技能安装和连接器都使用同一套运行、失败、等待、完成和验收状态。

## 3. 核心架构升级

### 3.1 任务运行内核

- 每次任务建立目标、完成标准、前置条件、当前假设、证据、产出物和验收状态。
- 执行后读取真实结果；失败按原因分类为环境、依赖、权限、网络、账号、版本、输入或方案错误。
- 连续无进展时切换本质不同的路线，不重复同类命令。
- 达到预算时生成强制交接：已完成、阻塞点、已尝试路线、用户唯一下一步和继续条件。
- 支持用户插话：立即确认、说明当前调整或排队策略，并在下一次模型返回前吸收新要求。

### 3.2 技能完整性与安装器

- Skill 不再以单个 `SKILL.md` 作为完整安装单位，而是以技能目录和清单为单位。
- 安装前检查 `SKILL.md`、`references/`、`scripts/`、`templates/`、许可证、运行依赖和最小版本。
- 为每项技能生成健康状态：可直接使用、需要安装依赖、需要账号授权、文件缺失、来源失效。
- 内置、我的技能和商城都展示来源、版本、最近检查时间和健康状态；损坏技能隔离，不误导模型调用。
- 支持从可信 GitHub 目录、压缩包和市场地址恢复安装；恢复前校验文件清单和内容哈希。

### 3.3 连接器与知识库

- 连接器统一为“配置、预检、授权、调用、验证、诊断”六段流程。
- Obsidian、网页知识库和未来服务共享相同的连接健康状态和权限提示。
- 不把未验证的连接器显示为“已连接”；失败时直接说明用户是否需要登录、授权或选择本地目录。

### 3.4 多员工协作

- 团队任务显示目标、负责人、依赖、当前阶段、可观察成果和验收人。
- 员工之间传递的是结构化交接：成果、证据、未决问题、风险和下一步，而不是长篇聊天记录。
- 审查失败只回退责任步骤，避免整个团队从头重跑。

## 4. 与现有产品的同质化记录

以下能力已具备，不在大版本中重复造轮子，只做统一和增强：

- 多模型员工、独立模型配置、团队编排和审批式项目草案。
- 助手的动态前置判断、失败诊断、换路线、最终自检和诚实的安装状态判断。
- 独立 Electron 聊天与设置窗口、主题、字体、员工头像和状态展示。
- 内置 Skill、我的 Skill、第三方市场入口、Obsidian 与网页知识库连接入口。
- 真实文件读写、附件落盘、产出物归类和可折叠执行记录。

## 5. 当前优先级

1. 技能完整目录安装、健康检查和损坏技能隔离。
2. 统一任务状态机，让助手、员工和团队共用同一套验收与交接结构。
3. 连接器预检与明确的授权/配置引导。
4. 太极品牌迁移：产品名称、窗口标题、发布说明、默认提示词和本地数据迁移策略。
5. 在上述基础稳定后，再做视觉体系与高级协作视图升级。

## 6. 验收标准

- 用户不再看到“操作很多但不知道成功没有”的结果。
- 一个 Skill 缺少配套文件时不会被标为可用。
- 任务失败时，用户能在一屏内知道是否要自己操作、要做什么、完成后如何继续。
- 同一任务的员工、团队和助手状态一致，且每个完成结论都能追溯到真实证据。
- 改名升级不丢失已有员工、团队、模型、聊天和技能数据。
