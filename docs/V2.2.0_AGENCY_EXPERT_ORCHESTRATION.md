# v2.2.0 专家团编排升级

更新日期：2026-07-30

## v2.2.1 补充：全部专家显示为办公室员工

- 用户验收后确认需要让全部专家作为真实员工显示在办公室，而不只是作为可选目录。
- 客户端初始化会保留现有人员、团队、聊天和任务，并自动补齐缺失的 268 位目录专家。
- 专家姓名直接采用其可提供的专业职责名称，职务栏展示所属部门；头像和头像框按专家 ID 稳定分配，重启后不会随机跳变。
- 每位专家分配真实工位。办公室工位数量由原先的固定 999 个空位改为最少 24 个、随实际工位增长，避免新增专家后无意义地渲染 999 张卡片。

## 产品方向

太极不迁移到 Tauri，也不替换现有 Electron 执行内核。目标是在已经具备本地工具、Skill、连接器、任务恢复和证据验收能力的基础上，吸收 `jnMetaCode/agency-orchestrator` 的优势：专业角色目录、按目标自动组队、先形成专业方案再执行，以及可追溯的阶段交付。

目标链路：

`用户目标 -> 项目简报 -> 专家匹配/组队 -> 专业方案 -> 用户批准 -> 可执行任务 DAG -> 真实产物与测试 -> 证据化交付`

章北海仍是唯一默认面向用户的常驻主助理。用户明确 `@员工` 时才由该员工回复。专家团是章北海的执行与评审能力，不应变成抢话、复述需求或刷屏的第二个聊天机器人。

## 本次已完成

### 1. 内置专家目录

- 已从公开的 `jnMetaCode/agency-agents-zh` 导入完整 **268** 个中文专家角色。
- 上游仓库许可证已核验为 **MIT**；每个专家条目保留许可证、来源链接、源文件路径、版本、部门、职责摘要和完整专业规则。
- 专家规则随 Windows 客户端打包，不依赖用户日后联网下载。
- 专家目录不默认把 268 人同时加入办公室。这样能避免侧栏、群聊和上下文被无关成员淹没，也避免每个任务把数百份提示词发送给模型。
- 在“添加团队成员”窗口中可以搜索完整目录，选择的专家会立即转为本办公室可执行员工，并继承当前全局模型或其后续独立模型配置。

### 2. 无人数上限和动态增员

- `Team.memberIds` 本身保持数组结构，没有人数上限。
- 项目执行中新增专家时，渲染端会更新团队名单，主进程执行器同步更新任务成员快照和内存成员表。
- 每次同步增加 `memberRosterVersion`，并写入执行事件，便于恢复、审计和排查。
- 后续的动态委派可以使用已同步的专家，不再因为启动任务时的旧成员快照而被拒绝。

### 3. 项目策划工件

- 新增版本化 `ProjectBrief`：目标、交付类型、假设、待确认项、专业阶段、阶段交付和验收标准。
- 项目草案会自动生成需求与范围、专业方案、实现或调研、验收与交付等阶段；阶段取决于任务语义，不能把所有任务硬塞进“必须有 HTML 文件”的模板。
- 用户批准后，项目简报会写入任务上下文，原生执行器按同一份目标、阶段和验收要求工作。
- 项目批准卡会显示项目策划和推荐专家，供用户在执行前调整或驳回。

### 4. 自动专家选择

- 项目草案匹配时，候选池由“当前办公室员工 + 268 位内置专家”组成。
- 用户已有员工优先保留；当现有人员没有覆盖所需能力时，系统可以推荐目录专家。
- 目前选择器使用能力图和任务语义能力标签，专家的部门、摘要和规则参与匹配与任务上下文。

## 本次没有完成，不能误报为已完成

1. **专业方案尚未由多位专家分别真实产出。** 当前 `ProjectBrief` 是可靠、持久的结构化计划，但仍是规则驱动的初始项目简报；下一版要让产品、UX、UI、架构、开发和 QA 专家各自形成有来源的结构化意见，章北海负责合并而非代写。
2. **执行 DAG 尚未完全由 ProjectBrief 驱动。** 现有 `TaskPlan/TaskRunner` 已有依赖和恢复能力，但批准后的项目仍主要使用现有线性步骤构建器。下一版需把项目阶段、依赖、负责专家、重试、审批点和验收映射成真正的 DAG。
3. **专家动态增员只完成了名单同步。** 已可安全纳入执行器并允许后续委派；尚未在项目看板中展示“为什么中途补人、由谁批准、补进后改了哪些阶段”。
4. **专家目录的独立管理页尚未完成。** 当前入口在团队成员选择器。后续需要单独的“专家目录”页面，用于按部门浏览、收藏、启用/停用、查看规则来源与加入办公室。
5. **语义选人仍需提升。** 能力图保证基础覆盖，但尚未达到 Agency 的 LLM 驱动角色组合深度。下一版要让模型输出可校验的角色建议、理由、空缺和替代方案，再由确定性校验器检查员工真实存在、权限和模型可用性。
6. **专家输出尚未结构化持久化。** 需要分别保存 PRD、用户流程、UI 规范、技术设计、实现方案、测试报告及其版本、引用和评审结果。
7. **尚未完成真实端到端 UI 自动化。** 当前电脑的 Electron GPU 子进程环境仍使真实 UI 回归不稳定；构建、原生执行、项目看板和打包核验已通过，但图形环境正常的机器仍需补跑 UI 回归。

## 使用限制

- 目录专家被选中后使用当前客户端的全局模型配置；没有可用模型时，任务仍会按现有前置检查阻止执行，不能伪装成专家已经工作。
- 目录完整规则会增加安装包和前端资源体积。这是“离线内置专业能力”的代价；后续可把规则拆分为按需加载资源，但不能改回依赖在线下载。
- 上游角色内容为 MIT 来源资料，应持续保留来源和许可证信息，不把第三方角色冒充为太极原创人格。
