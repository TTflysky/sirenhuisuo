## 评分口径

太极作为个人智能体研发项目约为 **80 / 100**；如果按可长期交付给普通用户的商业稳定软件衡量，目前约为 **60 / 100**。综合分数不是功能数量，而是智能体自主性、工程稳定性、可验证交付、安全边界和维护成本的加权结果。

## 现有优势

1. **任务不是一次性聊天**：TaskRun、Turn Lifecycle、证据账本、暂停/继续、失败恢复和用户插话已经形成可持续任务骨架。
2. **团队产品形态明确**：员工、团队、审批、分阶段执行与审核可以被用户直接看见，不只是后台提示词模拟多人。
3. **完成必须有证据**：文件、连接、命令和操作使用不同验收方式，已经开始摆脱“模型说完成就算完成”。
4. **发布流程可追踪**：预检、构建、安装包检查、GitHub Release 和交接文档形成了基本工程闭环。
5. **安全边界已经分层**：工作区、命令审批、连接器授权、敏感信息脱敏和高风险确认均有明确控制点。

## 主要短板

1. **语义到行动的编译仍不够稳定**：模型理解、确定性规则和调度器之间有时会丢失原始目标或职责，导致选错人、走错工具或重复执行。
2. **Coding 不是独立运行时**：目前缺少持续仓库索引、补丁级编辑、长命令会话、Diff 审查、测试选择和失败定位的统一闭环。
3. **核心模块过大**：`nativeExecutionAdapter.cjs`、`hermesClient.ts`、`store.tsx` 和 `theme.css` 都已超过两千行，修改容易产生跨层回归。
4. **测试结构偏脚本门禁**：仓库已有 79 个验证脚本，但常规 `test/spec` 文件为 0，组件行为和纯函数边界仍不够容易定位。
5. **模型接口仍以非流式 Chat Completions 为主**：长任务的首字响应、增量取消、工具并行控制和上下文利用率还有明显提升空间。

## Coding Runtime 升级建议

不应把任何外部产品整套“搬进来”，而应在太极现有任务内核旁新增独立的 **太极 Coding Runtime**：

- 建立仓库索引，按符号、依赖和最近修改定位上下文。
- 使用补丁级编辑而非整文件重写，保留可审查 Diff。
- 支持长命令会话、增量日志、暂停、恢复和超时分类。
- 固化“理解需求 -> 搜索代码 -> 修改 -> 构建/测试 -> 读取失败 -> 自主纠错 -> 证据验收”循环。
- 每项代码改动绑定工作树、测试证据、审查结果和回滚点。
- 让 Coding 员工、审查员工和项目调度器共享同一任务合同，但权限和责任相互隔离。

这条路线可以吸收成熟 Coding Agent 的工程方法，同时保留太极的员工、团队、记忆、审批和可视化优势。

## 下一阶段判断

太极已经不是空架子，但距离“像成熟 Coding Agent 一样持续理解、行动和纠错”还有明显距离。下一阶段最重要的不是继续增加表面入口，而是完成三件事：稳定任务语义编译、建立独立 Coding Runtime、拆分可测试的核心模块。完成这三项后，综合评分才有条件稳定进入 75 分以上。
