# 太极执行内核差异矩阵

更新时间：2026-07-28

这份文档记录太极与 `nousresearch/hermes-agent` 核心源码的对照结果。参考重点不是品牌、终端界面或提示词，而是 Hermes 如何持续工作、保存上下文、调用工具和处理失败。

## 根因结论

太极目前“不聪明”的首要原因不是模型本身，而是执行边界不够硬：模型可以给出合理的回复，但回复、工具结果、团队步骤和最终交付之间缺少一个持久化的状态协议。只要某次调用超时、窗口关闭、成员顺序变化或审查退回，系统就可能只保留文字，不保留下一步应该做什么的可靠状态。

## 对照矩阵

| 能力 | Hermes 关键结构 | 太极当前状态 | 优先级 |
| --- | --- | --- | --- |
| 持续执行循环 | `run_agent.py` 持续处理模型响应、工具调用和下一轮上下文，直到完成或达到预算 | 已有 `runAgentLoop`，但团队任务过去直接使用旧步骤队列，正式计划未成为门槛 | P0，已开始修复 |
| 工具注册与能力边界 | `tools/registry.py` + `model_tools.py` + `toolsets.py`，工具有注册、发现、可用性检查和场景工具集 | 有静态工具列表、Skill 和 Connector，但缺少统一的 `validateInput / dryRun / call / validateOutput` 协议 | P0 |
| 任务计划 | Hermes 有 todo、kanban 和 delegation 等可组合工具 | 太极已有 `TaskContract / TaskPlan`，本轮开始写入每个团队任务并按依赖取可执行步骤 | P0，已开始修复 |
| 状态持久化 | 会话消息写入 SQLite，带 session、工作目录和恢复信息 | `0.21.0` 团队模型与工具循环已迁入主进程原生 Adapter，沿用 JSONL 账本、Worker 租约、心跳和严格递增检查点 | P0，原生 Adapter 完成 |
| 轨迹与审计 | 保存完整 trajectory，过滤临时恢复消息，并支持压缩中间上下文 | `0.21.0` 后台工具与员工消息进入 TaskRun 投影，窗口关闭后继续执行并可重新回放；凭据只留内存 | P0，团队链路完成 |
| 上下文管理 | `memory_manager`、`session_search`、`context_compressor`、长期会话文件共同工作 | 有用户画像/长期记忆和短上下文拼接，但团队通常只取最近消息，缺少任务级摘要与检索 | P1 |
| Skill 使用 | Skill 工具可列出、查看、管理，Skill 提示词进入 agent 上下文 | 已有 Skill 健康检查、检索和原子安装，但缺少每个步骤的“选了什么、为什么选、读了哪些规则”结构化证据 | P1 |
| 失败恢复 | 错误分类、重试退避、模型切换、上下文修复和工具结果清洗分层实现 | 已有 `ExecutionController` 和模型重试；团队层还需要把失败结果绑定到计划步骤和责任人 | P0 |
| 多智能体委派 | `delegate_task` 创建隔离子任务，kanban 负责状态、心跳、阻塞和交接 | 团队成员是预先选出的顺序发言者，章北海尚不能可靠地动态创建、监控和回收子任务 | P1 |
| 工作区 | 工具以明确的项目/会话环境执行，记录 cwd 和 session | 太极已有每任务独立工作区和附件落盘，但还没有任务级 Git 工作树和跨进程 Worker | P1 |
| 安全与审批 | 工具、终端、外部服务按工具集和权限检查分层 | 已有沙盒、审批和敏感参数脱敏，需统一到 Connector/Runner 的同一状态机 | P1 |

## 本轮已落地

- 新增 `src/engine/taskRunner.mjs`：步骤状态、依赖、重试、审批、幂等记录、事件和恢复。
- 新任务保存 `contract`、`plan`、`runner`；旧任务加载时自动补齐。
- 团队执行循环在运行成员前检查 `dependsOnStepIds`，前置步骤没有完成时停止，不再跳过。
- 成员结果写回 runner；模型文字不再单独等价于“任务完成”。
- 新增 `scripts/verify-task-runner.mjs` 覆盖重试、依赖、审批、完成和恢复。
- `0.13.0`：新增 Electron 主进程任务运行快照，使用版本化 JSON 和临时文件替换写入；窗口启动先读兼容缓存，再异步以主进程快照校正，并自动迁移旧缓存。
- 主进程串行化任务快照写入，拒绝无效记录；读取到损坏快照时保留原文件并回退到兼容缓存，不静默覆盖。
- P1：新增版本化任务上下文快照，保存目标、验收标准、已确认决策、未决问题和最近执行事件；恢复任务时注入上下文，而不是只取最近聊天消息。
- P1：新增 Skill 使用证据，记录匹配、读取成功/失败、搜索和实际调用；任务面板显示最近 Skill 证据，避免“模型说查过”与“客户端确实读过”混淆。
- `0.15.0`：新增统一 Connector 协议，固定输入校验、权限、dry-run、真实调用、输出校验、脱敏和副作用幂等；协议元数据进入任务上下文，任务面板展示客户端连接器证据。
- `0.16.0`：文件写入、命令生成文件和审查结论统一产生版本化结构事件；审查退回会把责任步骤、修订步骤与复审步骤追加到正式 TaskPlan/Runner，并可随任务快照恢复。
- `0.17.0`：任务上下文升级为 v2，增加确定性/模型辅助压缩、中文历史任务检索、相似任务只读注入和上下文/Runner 事件回放。
- `0.18.0`：新增 Electron 主进程追加式任务事件账本；旧快照自动迁移，JSON 快照变为投影缓存，启动从 JSONL 回放，损坏尾部隔离恢复，回放界面显示账本完整性。
- `0.19.0`：新增主进程 Worker 控制平面与持久命令日志；团队运行前领取租约、持续心跳，跨会话租约安全暂停恢复，界面展示 Worker 状态和命令记录。模型/工具执行迁移到 Worker 是下一阶段。
- `0.20.0`：新增 Execution Adapter v1 检查点协议；普通步骤、审查和任务收尾按严格递增序号写回 Worker，主进程保护权威投影并拒绝旧渲染快照回退进度。模型/工具调用仍在渲染进程 Adapter 中。
- `0.21.0`：新增主进程原生 Execution Adapter 与工具运行时；Electron 团队任务关闭窗口后继续运行，消息与证据进入持久投影，运行中插话走独立控制 IPC，渲染执行器仅作为浏览器兼容回退。

## 后续实现顺序

1. 主进程原生 Adapter 已在 `0.21.0` 完成团队链路；下一步把内存 Job 升级为跨启动后台任务队列，并补等待用户、插话抢占和可靠恢复。
2. 把 Connector 协议扩展到内置验证连接器和后续插件注册表，并将跨重启幂等记录迁入任务运行存储。（动态 Action 首版已完成。）
3. 把每个成员步骤的 Skill 选择、Skill 读取、工具调用、文件写入和验收写成结构化事件，UI 只展示事件投影。（Skill、Connector、通用工具、文件与审查已完成首版，后续统一迁移与回放接口。）
4. 将审查退回绑定到责任步骤，生成修订步骤后重新进入计划图，而不是只依赖聊天内容中的 `REJECT` 文本。（`0.16.0` 已完成首版。）
5. 增加任务摘要模型、上下文压缩、会话检索和跨重启回放。（`0.17.0` 完成摘要检索，`0.18.0` 完成独立事件账本与完整性回放。）
6. 最后再引入动态组队、并发和真正后台 Worker；没有前面的持久化与验收约束时，动态组队只会扩大错误范围。

## 暂不直接照搬

Hermes 的 Python CLI、消息平台网关、Docker/SSH/Modal 后端和完整 MCP 生态不应直接塞进 Electron。太极当前最需要的是相同的内核语义：持续循环、工具注册、状态持久化、证据验收、失败恢复和可回放；实现可以保持 Windows 本地优先。
