# 太极 v3.8.0-v3.11.0 差异矩阵

日期：2026-08-04

| 领域 | v3.7 基线问题 | v3.11 已完成 | 仍有差距 | 下一阶段 |
|---|---|---|---|---|
| 原生执行 | Adapter 同时负责控制、步骤、补偿和投影 | 控制面、步骤执行器、策略、投影、自适应恢复分离 | Adapter 仍约 1438 行 | 拆队列协调与证据汇总 |
| Agent Loop | 模型客户端与执行循环耦合 | `hermesClient` 与 `agentLoopRuntime` 分离；固定来源策略独立 | 主循环最长函数仍约 850 行 | 抽工具周期与最终收尾 |
| Store | UI 状态、命令、恢复和团队调度集中 | Store 降至约 833 行；四类命令/运行时独立 | 团队 Runtime 主函数仍约 560 行 | 抽消息回调和阶段执行会话 |
| Worker 恢复 | 租约、心跳、检查点散落在团队回调 | `teamWorkerLease` 统一领取、心跳、递增检查点和释放 | 真实断电恢复仍需长期实机样本 | 故障注入与跨版本恢复 |
| 最终验收 | 完成判断混在团队 `onDone` | `teamRunFinalization` 按交付类型和审查证据统一收口 | 更多专业工件需要类型化验收器 | 插件化验收注册表 |
| 工程门禁 | 只检查文件总行数 | 增加 AST 单函数长度门禁与职责回流断言 | 阈值是当前冻结线，不是最终理想值 | 每轮只降低、不提高阈值 |
| 第二梯队 | `main/taskService/skills/nativeToolRuntime` 未纳入治理 | 已纳入函数增长门禁并形成公开审计 | `createWindow`、`createTaskService` 仍超长 | v3.12 起按状态所有权拆分 |
| 人格 | 人格未描述模块化事实源 | v24 明确模型、策略、Worker、阶段和验收边界 | 仍需真实项目检验语言与状态一致性 | 用失败样本继续修订协议 |

## 结论

本阶段不是把一个大文件机械搬成多个文件，而是为策略、控制、执行、恢复和验收建立独立状态所有权。当前架构已经更容易定位错误和局部测试，但 Agent Loop、团队讨论、窗口生命周期和 TaskService 仍有超长函数，不能把 v3.11 描述为重构完成。
